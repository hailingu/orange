# 测试与验证 — 从红绿循环到治理化的测试资产

对应索引:[README.md](README.md) › 文件索引。orange 的测试纪律贯穿所有
ADR:功能与缺陷修复走 **TDD 红绿重构**;纯文档走治理校验;一切验证命令
与证据必须可复现。本文按"方法 → 资产 → 治理"三层整理。

## 1. 红绿重构:真实的提交化石

仓库把"先红后绿"做成了**可考古的提交序列**(每条契约一个红提交 + 同
变更内的绿实现,ADR-0003 的 T-1 证据):

| 契约 | 红(先落的失败测试) |
| --- | --- |
| 空输入拒绝 | 提交 `12b0e43`:`parse_request("")` 必须 `nullopt`,观察到红(ctest exit 8)后才实现 |
| 请求行文法 | `3faf3d9`:三非空 token + 七种畸形拒绝,10/11 新检查红 |
| 错误分类 | `e739c68`:variant 错误套件,23/28 红 |
| RFC 9112 3 超长分类 | `db2856f`:14/48 红(501/414 归责规则) |
| 头部块文法 | `f9e6364`:36/84 红 |
| 响应成帧 | `87548eb`:38 检查的 `write_response` 套件对占位实现红 36(ctest exit 8),绿灯 `743b5ed` |

读法要点:

- "红"是**被观察并记录的**(`observed red at ... ctest exit 8`),不是
  "我猜它会挂"——没看到失败的失败测试不算数;
- 每次绿转红之间套件整体保持全绿(增量契约化);
- **重构是第三拍**:行为不变的整理(如 LUT 重构)不新增测试,靠特征化
  测试与对拍守住。

新模块的"红"有一个脚手架问题:头文件和符号不存在时套件**链接不起来**,
连红都观察不到。仓库的解法(T-1 task-2 先例 + 响应套件):先落**仅接线
的占位实现**——`write_response` 恒返回错误通道、零行为——配上完整测试
套件提交,观察红(36/38,两条故障注入检查被占位的"恒失败"意外满足,
这个计数差异如实写进提交信息),下一提交换成真实现转绿。占位实现让
"套件可链接"与"行为未实现"同时成立,红灯因此可观察、可提交。

另一个绿灯期教训:响应套件第一版把 7 字节的 CR/LF 夹具数成 6 字节——
**精确到字节的期望值断言让测试自身的错误也无处藏身**(37/38 卡住,对的
是实现、错的是测试),修正夹具后 38/38。测试代码会错,断言越精确,错
越早暴露。

## 2. 特征化测试(characterization tests)

重构前先把**现状行为**钉死:提交 `211c62b` 在换行搜索实现前,先用测试
固定"token 不能跨越首个 CRLF""裸 `\r` 留在 token 内"等既有语义。这与
"测试规格"不同——特征化测试不改判对错,只承诺**不悄悄变**;重构后对拍
0 差异,才能合入。遗产代码改造的安全网首选。

## 3. 差分/对拍测试(differential testing)

orange 反复用的三板斧:

- **实现间对拍**:旧实现 vs 新实现 vs 外部贡献,同输入比结果(LUT 重构
  16 输入三向 0 不一致;行搜索替换 13 输入 0 不一致);
- **喂法不变性对拍**:同一线字节用 17 / 8192 / 整块三种 feed 粒度,结论
  必须相同(见 [`parser-design.md`](parser-design.md) 第 6 节);
- **等价性靶**:`http_parser_equivalence` 作为常驻基准套件成员,任何
  优化 PR 自动对拍。

## 4. 模糊测试(fuzzing)与 sanitizer

- **种子化模糊**:200,000 输入的 seeded fuzz 跑在 ASan/UBSan 构建下,
  覆盖文法路径(ADR-0003 T-1 证据)。种子化 = 可复现,出问题能重放;
- sanitizer 捕获过真实缺陷:`parsed_of` 悬垂(stack-use-after-scope)
  与 NUL 夹具误编码 VT(0x0B)——**测试代码自己的 bug 也要靠工具抓**;
- sanitizer 跑法与平台限制见 [`build-and-toolchain.md`](build-and-toolchain.md)
  第 3 节。

## 5. 边界与矩阵思维

预算类逻辑的测试不测"大概超了",测**精确边界**:

- 元数据 8192 通过 / 8193 拒绝;1 MiB 内容按 512/1024 字节 chunk 编码
  (前者必拒、后者必成)——一字节与一档编码的差就是断言对象;
- 粘性错误:超限后持续 feed 保持错误,`reset` 后作为独立流恢复;
- 拒绝生命周期(CC-5):431/413 响应 → EOF → **被拒连接上无后续响应** →
  重连成功——把"关连接"当行为断言,不只是返回码。

## 6. 测试代码也是代码:治理它

- **超大测试的分解**(service ADR-0001):307 行代码的 `main` 被拆成
  14 个 ≤39 行的检查函数 + 24 行分派器,断言一条不增不减,两套 CTest
  靶前后皆绿——测试资产享受与生产代码同级的重构纪律;
- **测试夹具的资源生命周期**(项目 ADR-0007):治理校验器的
  `validRepository()` 曾在临时目录泄漏夹具(一次全量运行遗留 192 个目录),
  修复模式值得抄:
  - `temporaryDirectory(t, prefix)` 辅助函数**先注册 `t.after` 精确路径
    递归清理、再填充内容**(注册先于使用,防早退泄漏);
  - 所有权归测试上下文:正常完成与断言抛错都会执行 teardown(node:test
    的 `t.after` 语义);
  - 验证本身也成测试:`fixture-lifecycle.test.mjs` 用**真实子进程**验证
    成功/失败/已删根/并发四种场景的清理行为,并用"隔离 TMPDIR + 哨兵
    文件"证明全量套件跑完目录里只剩哨兵;
  - 并发隔离:两个测试进程各持不同根,互不误删(唯一命名,不用固定名)。
- **断言语义不锁文本**:仓库规则禁止测试断言文档的普通措辞/行数/排版,
  只允许断言机器可读契约(诊断码、wire 夹具、schema 令牌)——测试要
  验证语义,不是给文本上石膏。

## 7. CI 即验证,不是即产物

ADR-0009 工作流的两个自我约束(详见
[`build-and-toolchain.md`](build-and-toolchain.md) 第 4 节):

- 一切编译输出是一次性的,`if: always()` 收尾删除——验证不产生被保留
  的构建产物,治理上就不算"受治理构建"(Governed Build);
- 基准阈值是量级护栏:防的是**数量级回归**(100 ns 变 100 µs),不是
  追逐个位数百分比——共享 runner 的噪声水平决定阈值必须宽。

## 8. 证据纪律(贯穿所有 ADR)

每条验收检查的五要素,写死在 ADR 模板里:**二元判定点、前置条件、可执行
或确定性方法、精确可观察的期望结果、要留存的证据**。反例词汇被明令禁止
("works""reasonable""stable")——"独立评审者不需要解释成功是什么"
才算合格的检查。这与测试写作的普通常识完全同构:断言要精确到状态、
字节与退出码。
